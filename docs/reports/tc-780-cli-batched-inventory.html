TC-780 CLI inventory batching

Local PG18 equivalence and WAN-latency evidence · 9 October 2026

The final CLI completed dry-run in 2.111 s and apply in 2.106 s with 70 ms added to every PostgreSQL ready cycle. Both are below the 20 s target.

Change

The CLI now reads SQL and DuckDB artifact identity and metadata in one query, loads the existing aliases once, and classifies collisions in memory. Its existing set-based ability and invocation reads remain. Apply loads the existing quarantine, artifact, and alias sets once, then inserts new quarantine and alias rows with two multi-row statements inside the existing transaction.

The artifact query names nine metadata fields explicitly. Neither payload nor delta_payload appears in a production-facing inventory SELECT. The fence, drift verification, quarantine and set --authorized paths are retained.

Fixture and equivalence

A local PostgreSQL 18 fixture was cloned into separate old and new databases. It contains 715 SQL artifacts, 612,091 ability rows, and 1,546,356 invoked_abilities rows, matching the production row estimates recorded in /tmp/tc780-cutover/table-sizes.txt. Of the artifacts, 400 classify as unique, 100 as ambiguous, and 215 as unattributed. This synthetic fixture matches row counts; it does not reproduce production byte sizes or data distribution.

The old binary was built from branch base 5858bc28a2da06f96667cc2104f4da7d2d74c511. The final binary was built from the change. Byte comparisons passed for dry-run JSON and apply JSON, both directly and through the latency proxy. The same byte comparisons passed for 400 alias rows, 715 quarantine rows, one fence row, and explicit metadata exports of 715 artifact rows. The JSON output SHA-256 for both versions and both commands is 9b21ea10ebe3c27c89e43b4433683208b1cbae31afef9e488df3271d9aa1c908.

The CLI statement logs contain no SELECT of the artifact payload columns. An initial local row export selected the synthetic fixture’s empty payload columns; that export was discarded and replaced with an explicit metadata-only comparison. No production artifact payload was read.

Production connectivity check

Exactly five separate SELECT 1 calls were timed from this Mac using the private production URL. Their elapsed times were 1,143.5 ms, 912.0 ms, 1,023.0 ms, 2,289.8 ms, and 1,039.3 ms; median 1,039.3 ms. Each timing includes connection and TLS setup, so these numbers are an end-to-end trivial-query measurement rather than a pure steady-state network RTT. No other production queries were made.

Gates and deployed-node path

cargo fmt --all --check, cargo clippy --workspace --all-targets -- -D warnings, cargo test --workspace with a local PostgreSQL URL, and the separate CLI test target all passed.

The deployed N3 node calls the same database_migration module for the effective fence and SQL/DuckDB resolve during serving. It does not call inventory or apply at boot or while serving; those entry points are called by the operator CLI. Shipping this CLI from the new branch does not require rebuilding the existing N3 image.

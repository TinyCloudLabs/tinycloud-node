# TC-959: tinycloud-node Better Stack log shipping

## Transport and gate

The node and `dstack-ingress` use Docker's `gelf` logging driver with the exact service labels `tc.logship=tinycloud-node` and `tc.logship=tinycloud-ingress`. Both send UDP to `127.0.0.1:12201`. Vector listens inside its own bridge network at fixed address `10.255.253.2`; that network is not shared with app or Postgres services and has egress for Better Stack. The only published Vector port is `127.0.0.1:12201:12201/udp`. Vector has no `docker.sock` or `/var/lib/docker` mount. There is no DockerRootDir pre-deploy check.

`logship_gate` is the first transform. It reads `_tc.logship` as a string and accepts only the two exact labels. Unlabelled, malformed, and unknown-message inputs increment bounded counters; wrong labels increment a separate bounded counter. One `logship_gate_summary_total` event per minute carries the four reason counts without source content. After the gate, `strip_gelf_fields` reconstructs the event from only the approved label and GELF `message`, dropping all underscore-prefixed fields and dockerd metadata. `parse_gelf_message` then parses `.message`, the app's JSON line. The existing inner allowlist and schema projection feed the existing priority lanes and `budget_size_guard`; gate summaries have an independent lane, and the guard remains the sink's sole input. Ingress non-JSON stderr is dropped after the gate.

The node JSON formatter caps the complete serialized line, including its newline, at 15,000 bytes by truncating the longest string values with a fixed marker; if a line still cannot fit or parse, it emits one fixed valid JSON marker record. The panic hook uses the same path. This keeps node lines below Docker's 16 KiB GELF fragmentation threshold. Ingress logs only fixed route/method maps, protocol, and numeric request data rather than raw paths or headers. Its `$upstream_status` and `$upstream_*_time` variables can contain comma-separated retry values; the checked ingress files set no explicit retry/list bound, so a strict <16 KiB ingress-line bound is not proven. GELF reassembles complete chunks; incomplete frames are rejected rather than forwarding partial text. There is no checkpoint or replay state.

The node and ingress do not depend on Vector. Their GELF logging driver is UDP and does not require Vector to start. A missing Better Stack token leaves Vector idle. Postgres and every non-shipped service remain unlabelled and use capped `json-file` logs.

## Redaction and alerting

The allowlist excludes signed-KV tickets, authorization headers, tokens, transcript text, SQL values, meeting URLs, X-Forwarded-For and CF-Connecting-IP values, IPv4/IPv6 addresses, raw paths/IDs, UCAN/SIWE/delegation strings, owner DIDs or wallet addresses, space IDs, e-mail addresses, nested objects, arrays, and all unknown keys. Unknown ingress paths collapse to `<unmatched>` only after the raw route string passes its 256-character bound. The panic hook emits only a fixed JSON message and does not serialize panic text or source location; input level cannot forge the panic alert. See `log-shipper/vector.tests.yaml` for forbidden-value, malformed-value, priority-lane flood, route-template, multi-upstream, fixed-panic, GELF gate, metadata-stripping, and counter tests.

At go-live, create a Better Stack alert for `event = node_fatal_panic` and one source-silence alert per service, within free-plan limits. The lead's GELF/UDP spike passed restart/recreate recovery, 500-line outage-burst recovery, sibling forgery, and external-interface isolation. It also observed no app blocking. The full node-specific Docker acceptance script is review-only and has not been run here.

## Priority and monthly volume budget

The panic lane allows 2 events/minute; node app ERROR and WARN each allow 5/minute; the gate summary allows 1/minute; ingress allows 26/minute. The four gate-reason counts share one content-free summary event and cannot consume the 5/minute app WARN allowance. Each lane feeds `budget_size_guard` directly without entering the ingress throttle. The ingress lane carries per-minute `(route, status_class)` failure counts, per-minute route-only success counts, and slow requests. A 2xx/slow request is counted and marked slow; route cardinality is bounded to 35 known templates plus `<unmatched>`.

At the 281-byte final event-size limit, the worst case is `(2 + 5 + 5 + 1 + 26) × 60 × 24 × 30 × 281 = 473,428,800 bytes` (0.473 GB/30d), within the node's 0.48 GB allocation of the shared 3 GB free quota. The per-lane ceilings are 24,278,400 bytes for panic, 60,696,000 bytes each for app ERROR and WARN, 12,139,200 bytes for the gate summary, and 315,619,200 bytes for ingress. These are hard ceilings assuming every allowed event reaches the sink; shared quota use by other sources is separate.

## CVM resource and disk budget

The CVM is tdx.medium: 2 vCPU, 4 GiB RAM, 20 GB disk. Vector runs as UID 10001 with 64 MiB memory/swap and a CPU limit of ≤0.5 CPU (25% of the 2-vCPU CVM), read-only root, all capabilities dropped, and `no-new-privileges`. Its `data_dir` is an 8 MiB tmpfs; the token file is mode 0600 under that same tmpfs. There is no volume initializer, Docker log-tree mount, or persistent checkpoint volume. Vector and ssh-gateway each have capped `json-file` logs (`10m × 3`), a 60 MB combined retention ceiling. Node and ingress logs travel through GELF rather than a local log file. The review-only acceptance harness measures Vector peak memory and reports 5,000-line burst loss; neither value has been measured by this change.

## Secrets and local-log exceptions

The ingest host is configured once as `BETTERSTACK_SOURCE_HOST` and substituted into the sink URL. The source token is GitHub `production` environment secret `PROD_TINYCLOUD_BETTERSTACK_SOURCE_TOKEN`, written to the sealed environment as `BETTERSTACK_SOURCE_TOKEN`. The entrypoint writes `SECRET[bs.bs_token]` into `/var/lib/vector/secrets/bs_token` on Vector's tmpfs, with a restrictive umask, then unsets the token and config variables and executes Vector. Production uses `unset …; exec vector`; `exec env -u` is used only in the acceptance override. The token is not in Vector's process environment. It remains in the container's configured environment (visible to `docker inspect`) and in the init process's initial environment, which only principals that can already read the tmpfs token file can read. Restrict access to the tmpfs and Docker daemon/API; the token is not committed or logged.

Only node and ingress logs carry `tc.logship`. Vector and ssh-gateway retain capped, unlabelled `json-file` logs and are not shipped, preventing self-ingestion. Postgres is not mounted into Vector.

## Verification and deploy gate

CI checks the canonical common + `services.tinycloud-node` schema, generated VRL, byte-identical embedded Compose config, structural packaging restrictions (`configs.*.file`, `env_file`, and relative bind sources), and native Vector 0.59.0 validation/tests after verifying the release tarball SHA256. Native preflight uses a disposable dummy token fixture only; the acceptance override config is mode 0644 for Vector UID 10001, and the rendered ingress producer command asserts `$$` escaping. The review-only `tc-959-node-docker-check.review.sh` covers 5× each Vector restart, crash/restart-policy, and recreate; 3× Vector-down 500-line bursts; app service continuity; a host-loopback and a logship-network positive control (each source +1 and shipped +1); then exact zero source/shipped deltas for node, ingress, Postgres and host-interface probes; `/version` while Vector is stopped; and Vector memory. Its Prometheus parser matches the exact GELF source label set and reads the value field before any timestamp. The test-only node override uses local Postgres, a Static test key, TEE Off, and no dstack socket. Only the native preflight and Docker-free dry run were executed; Docker acceptance remains unverified and requires explicit Docker authorization. Amos owns production deployment and go-live alerts; do not use this runbook to deploy or change secrets.
